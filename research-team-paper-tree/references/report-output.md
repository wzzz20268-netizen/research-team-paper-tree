# 输出 Markdown 与交互网页

先写原论文的问题和阅读路线，再写各分支，最后放团队证据和检索细节。标题应该说出读者将看到的问题，例如「运动规律猜错了，雷达还能跟上吗？」。「先做什么、遇到什么困难、下一篇改变了什么」各用具体事实说明；若几篇工作并行，只写它们解决的不同问题。阅读路线用少量代表论文即可；完整清单仍保留。论文的原题及专业术语可查，正文从读者熟悉的现象讲起。

将核实材料整理为临时 UTF-8 JSON，用本 Skill 的脚本一次生成两份文件。以下命令中的脚本路径以 Skill 目录为基准。

```text
python scripts/render_report.py report-data.json --output-dir <用户的输出目录> --name <报告文件名前缀>
```

交付生成的 `<前缀>.md` 和 `<前缀>.html`。HTML 本地双击即可打开。文件间的链接需要两份成品同目录。临时 JSON 仅在用户需要可编辑中间数据时交付。Python 不可用时，直接用相同资料制作 Markdown 和自带样式的 HTML，保留以下交互和信息字段。

## 数据结构

所有文字用纯文本填写，长段落可用空行分隔。所有来源列表使用 `[{"label":"可读的来源名","url":"https://…"}]`。没有查证到的内容应说明欠缺的证据。数据模板示意如下。

| 位置 | 字段 |
| --- | --- |
| 顶层 | `title`、`overview`（用白话介绍原论文和报告范围）、`seed`（原论文 ID）、`lang`（如 zh-CN）、`papers`、`groups`、`reading`、`clues`、`coverage`、`relations`。 |
| `papers` 中的每项 | `id`、`title`、`date`（YYYY、YYYY-MM、YYYY-MM-DD 或空字符串）、`authors`、`venue`、`summary`（做了什么）、`sources`。可选 `label`（中文短名，用于图中）、`found_by`（实际发现入口）、`reason`（关联和收录理由）、`affiliation`（外组归属）、`note`（版本日期或待核实证据）。种子论文及推荐论文应写 `found_by` 和 `reason`。各版本用具名链接列在 sources，并在 note 记各自日期。 |
| `groups` 中的每项 | `name`、`profile`（段落列表，段落格式见下）、`branches`（每项含 `title`、`kind`（例如主干、旁支）、`story`（问题、种子联系、后续各项如何分工或推进）、`papers`（论文 ID 列表））。研究组已确认但暂无成果时可用空 branches。合作论文可在多个组出现，每组只列一次。 |
| `reading` 中的每项 | `paper`（论文 ID）、`reason`（为什么此时读）。 |
| `clues`、`coverage`、`profile` 中的每项 | `title`、`text`、可选 `sources`。clues 说明线索来自哪、用它怎么查、查到了什么。coverage 列检索日期、范围、检索式、计数、限制和待核实项。profile 保留通讯作者映射和团队事实。 |
| `relations` 中的每项 | `anchor`（本组论文 ID，或无确认团队时用种子 ID）、`paper`（外组论文 ID）、`type`（带方向，如「原论文引用此文」）、`evidence`（用白话说明关系和证据）、`sources`。外组 ID 不加入本组的 branches。尽量用原文显示引用语境。对仅有主题相似的条目，给双方各自的来源以便读者比较。 |

例如某分支的 `story` 可以写「早期工作在模拟数据里试着解决测量误差。第二篇把设定搬到真实路况，检验原来的办法遇到车速变化还能否使用。」正文的每句时间关系和结果都应由材料支持。论文 ID 使用字母、数字、连字符或下划线，限制在 64 字符内。大量论文时可按实际需要增加相邻分支，每份成品仍保留完整条目。

## 交付前核对

- Markdown 和网页的组、论文、版本状态及外部关系一致。网页从种子与团队分支开始，分支、论文详情可以展开，且能跳到推荐读的那一篇。外组连接标出方向或相似类型和证据。
- 让读者只读分支介绍就能回答「它在研究什么」「跟原论文有什么关系」。再沿时间线说明代表论文之间可验证的变化。
- 检查内部跳转、原文链接、顺序、重复 ID、证据缺口与论文统计。用浏览器打开生成的 HTML，试一次分支展开和外组关系。如果无法访问浏览器，核对生成结构，并注明验证范围。
